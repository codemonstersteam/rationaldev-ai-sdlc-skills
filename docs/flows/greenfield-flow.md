# greenfield-flow — вертикаль GREENFIELD (v0 → 1.0.0)

## Зачем этот вес

**Сервиса или CLI ещё нет — строим первую вертикаль с нуля.** Задача не в том, «что сломается»
(ломать нечего), а в том, чтобы вообще появился контракт: публичный API, который потом судят все
остальные веса. Поэтому greenfield ведём полным дизайн-пакетом — от требования к замороженному
контракту, дереву модулей, README и рабочему скелету из шаблона. На выходе транк получает **`1.0.0`**:
по SemVer это и есть первый публичный релиз, «версия, которая определяет публичный API».

Greenfield — **хребет всего конвейера.** Его вторую половину (акцепт плана → реализация → приёмка →
git → мерж → закрытие) наследуют веса `patch`, `minor`, `major`; отличаются они только головой.
Полный дизайн живёт здесь один раз, дальше переиспользуется.

## Инвариант веса

Публичного API ещё нет, поэтому решающая ось SemVer (обратная совместимость) здесь не применяется:
вопрос не «что сломается», а «есть ли вообще контракт». Итог прогона — замороженный контракт: с этого
момента он и есть та самая документированная поверхность, совместимость которой будут судить все
последующие изменения. **Тоггла в этой вертикали нет — ломать ещё нечего.**

**Причина ≠ вес.** Правка существующего кода в один модуль без смены контракта — это не greenfield,
а `patch` (см. [`patch-flow.md`](./patch-flow.md)). Новый код в один модуль — вырожденный greenfield:
он всё равно планируется как обычная модульная задача, а не в обход дизайна. Задача на два и более
модуля или несколько сервисов (эпик) не ведётся — харнес честно останавливается с вопросом к оператору.

Несколько понятий, которые встретятся ниже, объясняются один раз:

- **Форма проекта (`service` | `cli`)** — это вертикаль шаблона, а не ветка в поведении ролей. От неё
  зависит форма контракта (HTTP-спека либо схемы конфига и отчёта), шаблон скелета и разделы README;
  сами стадии одинаковы.
- **Замороженный контракт** — спроектированный один раз и помеченный неизменяемым: дальше код следует
  за ним, а не наоборот.
- **Прогон закрывается явно.** Пока задача идёт, её состояние живёт в служебной папке; после мерджа
  отдельная роль стирает это состояние, оставив запись в реестре изменений. Без явного закрытия
  согласие по прошлой задаче могло бы случайно пропустить следующую через гейт.

Репозиторий строит сам харнес: стандарт **задаётся** им, а не подбирается под чужой репо. Никакой
разведки и conform-режима нет, набор ролей закрыт.

## Точный контур для исполнителя

Поток идёт сверху вниз: фронт-дор превращает сырое требование в измеримое, триаж ставит вес,
интейк разворачивает требование в FRD, нарезка бьёт его на атомарные срезы. Дальше — проектирование:
по каждому срезу пишутся use-case, **контракт проектируется ровно один раз на весь сервис** и
замораживается, затем по каждому срезу строится дерево модулей, и один раз — корневой README.
По готовому дизайн-пакету нарезаются тикеты (scaffold первым, он блокирует всё), собирается план,
проходит одно ревью — и план уходит на человеческий Gate #1. После акцепта режется рабочая ветка,
скелет, компонентные тесты RED, модули, приёмка DoD, коммит и PR, Gate #2 на мерж, закрытие прогона
с тегом `1.0.0` и, наконец, канарейка с Gate #3.

## Тиры

**large = суждение** (gilb, triage, intake, slicer, usecase, apidesigner, moduledesigner, dijkstra, ticketer,
planner, mills, linger, fagan). **medium = реализация** (hughes, michtom). **small = механика**
(scaffolder, wirth-tester, git-hand, ledger). Greenfield — самая дорогая вертикаль: почти вся голова
конвейера это проектные решения, которые дальше **переиспользуются** всеми SemVer-вертикалями.

## Раунды

- Dropout стадии (пусто / ошибка / нет артефакта **по точному пути**): **retry ≤2** тем же владельцем → `escalate`.
  `STOP: <reason>` — это **не** dropout: он идёт оператору, харнес останавливается.
- Фикс-петля `@linger`: **K=2** (гардрейл режет третью попытку) → `escalate`.
- Ревью: счётчик держит `@mills` (раунд ≥1 с блокером → `escalate` → решает оператор на Gate #1).
- `PARTIAL:` от `@wirth-ticketer` — остаток дописывает **только он же**.

## Мониторинг процесса

- **Anti-loop:** гардрейл ловит субагента, повторяющего действие без прогресса → dropout → эскалация izi.
- **Watchdog:** плагин на `session.error` (провайдер отвалился) подталкивает izi «продолжай с текущей точки».
- **Идемпотентность/resume:** append-only `.agent/planner/done.log`; перед делегированием тикета izi **грепает**
  его там и **пропускает** уже зелёный. Продвижение только при `green`-маркере **И** чистом `validate-layout`
  (маркер = «произведено», гейт = «положено правильно»).
- **Видимость:** живая строка izi на каждый шаг (роль + izi-имя) + `node harness/progress.mjs .` — фазовая
  полоса читается из реальных артефактов, рисовать её руками запрещено (галлюцинация зелёного тикета).
- **Человеческие гейты не прокликиваются:** #1 план, #2 мерж, #3 прод. Маркер ставит только гардрейл по
  точному токену; самоакцепт izi — нарушение.
