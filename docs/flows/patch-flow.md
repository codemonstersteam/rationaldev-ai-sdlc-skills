# patch-flow — вертикаль PATCH (`x.y.Z+1`)

## Зачем этот вес

**Код разошёлся с задокументированным контрактом — правка возвращает соответствие.** Дефект в том,
что программа ведёт себя не так, как обещает её публичный API; patch чинит поведение, **не трогая сам
контракт** и не добавляя новых модулей — чинится скрытое решение (реализация) существующего модуля.
Транк получает `Z+1`.

Patch — **базовая SemVer-вертикаль.** Веса `minor` и `major` описаны как **дельта** к ней: они берут
тот же хребет и добавляют к нему свою голову. Поэтому patch стоит читать первым.

## Инвариант веса

Решающая ось одна — **обратная совместимость документированного контракта**, а не «баг это или
поведение». Контракт на patch не трогается вовсе: если правка требует эволюции спеки, это уже другой
вес — задача останавливается и переклассифицируется. Канарейка на patch есть **всегда**: контур
релиза один, быстрой полосы для правок не бывает. Тоггла нет — чинится существующее поведение, новой
способности не появляется; **рискованный фикс за тогглом — опция оператора, а не правило вертикали**.

**Причина ≠ вес.** Багфикс, который **сам** ломает совместимость (потребитель зависел от старого
вывода), — это `major`, а не patch. Аддитивная новая способность — `minor`, а не patch.

Несколько понятий, которые встретятся ниже, объясняются один раз:

- **Дискриминирующий сценарий (old ≠ new на данных).** Правку нужно доказать тестом, который на
  конкретных данных даёт разный результат до и после: старое (дефектное) значение ≠ новое (верное).
  Если выходы совпадают — тест слеп к изменению, и это находка о доработке входа теста, а не повод
  отгружать без проверки.
- **Радиус ряби решает дизайн, а не вес.** Оси ортогональны: вопрос не «сколько модулей», а «известен
  ли способ починки». Одна очевидная однородная правка без выбора — дизайн можно пропустить; правка,
  которая сама есть **решение** (конкурирующие подходы, новая абстракция, договорённость между
  несколькими модулями), — дизайн нужен. Радиус (по Парнасу: где именно скрыта затрагиваемая деталь)
  судит роль интейка изменения.
- **Change-dir** — отдельная папка изменения `docs/design/<slice>/changes/<NNN-slug>/`: план и тикеты
  правки живут в ней, а не поверх исходного greenfield-пакета среза.
- **Прогон закрывается явно.** Состояние задачи живёт в служебной папке только пока прогон открыт;
  после мерджа его стирают, оставив запись в реестре изменений. Реестр даёт идемпотентность, вайп —
  целостность гейтов: иначе согласие по прошлой задаче пропустило бы следующую.

Репозиторий построен самим харнесом: замороженный контракт и дизайн-пакет уже в нём, разведки и
conform-режима нет. Greenfield-роли проектирования и скаффолда в этой вертикали не запускаются.

## Точный контур для исполнителя

Поток короче greenfield: фронт-дор и триаж ставят вес, затем интейк изменения анализирует рябь —
какие модули затронуты, известен ли способ починки (радиус) и как выглядит дискриминирующий сценарий.
Дизайн включается **только если способ починки — это решение**; иначе сразу тикеты. Покрытие идёт
туда, где различие **наблюдаемо**: дошло до эндпоинта — компонентный тест, осталось внутри модуля —
дискриминирующий юнит. Дальше план, одно ревью, Gate #1, ветка `fix/`, точечная правка существующего
модуля на месте, приёмка DoD, PR `fix:`, Gate #2, закрытие с тегом `Z+1`, канарейка, Gate #3.

Легенда: **In** — вход · **Out** — выход · **✓** — чем проверяется · **⟳** — раунды · **тир** — тир и почему.

**no-bump:** если дифф оказался чисто плумбинговым (`.github/`, `*.md`, `docs/`, `Dockerfile`, lock-файлы),
`semver-bump` вернёт `tag=null` — **нормальный исход**, а не отказ: тега нет, канарейки нет.

## Тиры

**large = суждение** (gilb, triage, change-intake, moduledesigner, ticketer, planner, mills, linger, fagan).
**medium = правка кода** (hughes-rework, michtom). **small = механика** (wirth-tester, git-hand, ledger).
Patch экономичен: тяжёлые только анализ ряби и приёмка — имплементация точечная.

## Раунды

- Dropout стадии (пусто / ошибка / нет артефакта по **точному** пути): **retry ≤2** тем же владельцем → `escalate`.
- `STOP:` — не dropout: идёт оператору, харнес останавливается; чинить/импровизировать запрещено.
- Фикс-петля `@linger`: **K=2** (гардрейл режет третью попытку) → `escalate`.
- Ревью: счётчик держит `@mills` (раунд ≥1 с блокером → `escalate`).

## Мониторинг процесса

- **Anti-loop:** гардрейл ловит субагента, повторяющего действие без прогресса → dropout → эскалация.
- **Watchdog:** плагин на `session.error` подталкивает izi продолжить с текущей точки.
- **Идемпотентность/resume:** `.agent/planner/done.log` (append-only) — izi грепает тикет перед делегированием
  и **пропускает** уже зелёный; продвижение только при маркере **И** чистом `validate-layout`.
- **Видимость:** живая строка izi на шаг + `node harness/progress.mjs .` (полоса фаз между Gate #1 и Gate #2),
  вывод **дословно** — рисовать полосу руками запрещено.
- **Человеческие гейты не прокликиваются:** #1 план, #2 мерж, #3 прод.
