# rationaldev — концепция

Разработка ПО, где команда — это **человек и машина вместе**. Инженер думает над задачей
с ИИ и пишет код с ИИ. ИИ здесь не «инструмент рядом» — это часть самой работы.

Практически это **набор ролей-агентов**, который ставится в репозиторий. Вы даёте задачу —
агенты проводят её по этапам SDLC сами: от требования до версии-тега на транке. Дальше
называем эту машинерию «харнес».

## Зачем это нужно

Обычный AI-ассистент — один агент-«всезнайка»: он и планирует, и пишет, и сам себя проверяет.
Отсюда две беды. Первая — никто не отвечает за качество: тот, кто написал код, его же и
принял. Вторая — нет остановок для человека: агент едет до конца без вашего согласия.

Харнес решает это так:

- **Роли с контрактами вход/выход** вместо одного агента. Кто создаёт артефакт — тот его
  **не принимает** (проверяет другая роль).
- **Три места, где процесс ждёт человека:** план, мерж, релиз. Без вашего слова дальше не едет.
- **Версия ставится автоматически** после мерджа — без ручной арифметики.
- **Меньше тестов, но по делу:** качество закладывается проектированием, а не отладкой.

## Как всё держится: одна ось — вес по SemVer

Главная идея концепции — **у любой задачи есть вес**, и вес полностью определяет, как её вести.
Вес берём из [SemVer 2.0.0](https://semver.org): формат версии `MAJOR.MINOR.PATCH`.

Вес решает **один вопрос: ломает ли изменение обратную совместимость документированного
контракта** (публичного API — OpenAPI/CLI-спека). Не «сложно или просто», не «большая задача
или маленькая» — только совместимость.

**Важная ловушка: причина ≠ вес.**
Багфикс, который сам ломает совместимость (клиент зависел от старого поведения), — это **major**,
а не patch. Чистый рефактор без изменения поведения — **patch**, самый лёгкий вес.
Если из требования вес определить нельзя — агент **останавливается и спрашивает вас**. Выдумывать
вес запрещено.

## Пять вертикалей

Вертикаль — это конвейер одного веса: от требования до тега. Их пять.

| Вес | Когда | Версия (x.y.z) | Тесты и особенности |
|---|---|---|---|
| **[greenfield](docs/flows/greenfield-flow.md)** | сервиса/CLI ещё нет (v0 → v1) | `1.0.0` | полный дизайн с нуля: контракт → модули → README → скелет из шаблона |
| **[patch](docs/flows/patch-flow.md)** | багфикс, контракт **не** меняется | `Z+1` | код разошёлся со спекой — правка возвращает соответствие |
| **[minor](docs/flows/minor-flow.md)** | новая способность, аддитивно | `Y+1.0` | старые вызовы не затронуты; новое едет **выключенным** |
| **[major](docs/flows/major-flow.md)** | несовместимое изменение | `X+1.0.0` | нужна миграция; в PR — список ломающих изменений |
| **[chore](docs/flows/chore-flow.md)** | обвязка репо: CI, Dockerfile, конфиги, доки | **нет тега** | продуктовый код и контракт не трогаются |

Пояснения к колонкам:

- **Версия** — насколько двигается тег на транке после мерджа. У `chore` версия не двигается
  вообще, и это **нормальный исход**, а не ошибка.
- **Тоггл (фиче-флаг).** У `minor` новая способность **обязана** ехать выключенной по умолчанию:
  сломать нечего, зато можно спокойно катить. У `greenfield` тоггла нет — ломать ещё нечего.
  Включение способности — отдельная задача позже.
- **Аддитивность minor проверяется машиной**, не на глаз. Если проверка находит слом
  совместимости — вес был выбран неверно, задача останавливается и переклассифицируется как
  `major`.

Пошаговые сценарии каждой вертикали — в [`docs/flows/`](docs/flows/).

## Стандарт разработки — общий для всех вертикалей

Шесть принципов, одинаковых для любого веса.

| Принцип | Суть | Следствие |
|---|---|---|
| **SemVer** | вес = совместимость | транк получает версию-тег после мерджа |
| **API-first** | контракт первичен и **заморожен** до кода | код следует контракту, не наоборот |
| **Doc-as-Code** | README/ADR/дизайн живут в репо | документация ревьюится и проверяется машиной |
| **Git-TBD** | короткая ветка от свежего транка, один PR, частый мерж | незавершённое — за фиче-тогглом, релиз — канарейкой |
| **Проектирование** | дерево модулей; модуль прячет изменчивую деталь за **стабильным интерфейсом** | правка детали не выходит за пределы модуля |
| **Тесты по формуле** | качество закладывается дизайном | тестов ровно столько, сколько нужно (см. ниже) |

**Скрытая деталь за стабильным интерфейсом** (принцип Парнаса, information hiding): модуль прячет за
интерфейсом одну деталь, которая может измениться, — формат данных, алгоритм, протокол. **Пока интерфейс держится,
меняется только внутренность модуля**, и правка не расходится по коду. А когда меняется сам интерфейс — это уже
смена контракта, и её ловит вес (SemVer). («Секрет» у Парнаса — это скрытое решение, не пароль/токен.)

**Формула тестов.** Качество достигается проектированием, поэтому тестов минимум и они по правилу:

- **юниты** — `1 happy-path + по одной ветке на каждое условие`;
- **компонентные** — проверка поведения на границе контракта (чёрный ящик);
- **контрактные** — согласованность между компонентами (утилита
  [`pinout`](https://github.com/codemonstersteam/pinout)).

Корректность самих модулей доказывается **композицией** (предусловие/постусловие), а не перебором
тестами. Безопасность закладывается на планировании плюс security-скан в CI.

## Три человеческих гейта

Процесс останавливается и ждёт вас в трёх точках. Проскочить их автоматически нельзя — согласие
подтверждается точным словом-токеном.

| Гейт | Что принимаете | Как подтвердить |
|---|---|---|
| **#1 — план** | план работы до начала кода | `GATE1 APPROVE` |
| **#2 — мерж** | вливание PR в транк | `GATE2 APPROVE` |
| **#3 — релиз** | прод после канарейки | вердикт по 4 сигналам (см. ниже) |

## Никаких тестовых сред — только канарейка

Стендов и тестовых окружений нет. Готовый код едет **канарейкой прямо в прод**: за фиче-тогглом,
сначала на 1% трафика, потом 5% → 25% → 100%. Среда любая — виртуалка, контейнер, serverless
(k8s не обязателен).

Здоровье выката меряется **4 золотыми сигналами**: задержка, трафик, ошибки, насыщение ресурсов.
Пограничные сигналы — долю держим. Плохие — откат (тоггл OFF) и разбор.

## Закрытие прогона — из состояния в запись

Пока задача идёт, её состояние живёт в служебной папке `.agent/`. После мерджа задача **закрывается**
одним детерминированным шагом в строгом порядке:

1. **пруф мерджа** — подтверждение, что PR действительно влит (не просто «CI зелёный»);
2. **тег** — на транк ставится новая версия (арифметика по весу, форма тега — как у прошлых тегов
   репо; если тегов нет — префикс `v` по умолчанию);
3. **запись** в `docs/changes/LEDGER.md` — самодостаточная строка о том, что сделано;
4. **очистка** служебного состояния `.agent/`.

Порядок важен: очистка стирает то, что читают первые шаги. Без явного закрытия согласие по
прошлой задаче могло бы случайно пропустить следующую.

## Что харнес НЕ делает

- **Ведёт только свои репозитории** — те, что построил сам по стандарту (замороженный контракт,
  дизайн-пакет, своя парадигма тестов). Стандарт **задаётся**, а не подстраивается под чужой репо.
- **Не подстраивается под чужие парадигмы тестов** — работа с «неродным» репо вне контура.
- **Не водит эпики** (задачи на 2+ модуля или несколько репозиториев): такое честно
  распознаётся и **останавливается** с вопросом к вам.
- **Нет стендов и тестовых сред** — только CI и канарейка.

## Роли-агенты (кратко)

Внутри работает команда из ~15 узких ролей: фронт-дор превращает сырое требование в измеримое,
классификатор определяет вес, проектировщики готовят контракт и дерево модулей, разработчики пишут
и правят код, отдельная роль принимает работу, отдельная — ставит тег, отдельная — ведёт канарейку.
Набор ролей **закрыт**. Ключевой принцип — **асимметрия**: кто сделал артефакт, тот его не принимает.

Полный список ролей и их контракты — в [`docs/00_PROCESS.md`](docs/00_PROCESS.md) и
[`skills/roles/`](skills/roles/).

## Научный фундамент

Процесс стоит на классике структурного программирования.

| Идея | Источник |
|---|---|
| программа = дерево модулей, декомпозиция сверху вниз | **Niklaus Wirth**, *Systematic Programming* |
| модуль прячет одно изменчивое решение (information hiding) | **Parnas** |
| корректность по построению, а не отладкой | **Mills**, Cleanroom |
| структурный подход к программе | **Hughes & Michtom**; **Linger, Mills, Witt** |

Дисциплина выросла из цикла статей автора на **codemonsters.team**; отправная точка —
[«Дисциплина проектирования программ»](https://codemonsters.team/blog/2026/05/01/rational-design-discipline/).

## Что я изменил и почему

1. **Начало — с боли инженера, а не с терминологии.** Добавил секцию «Зачем это нужно»
   (один агент-«всезнайка» → две беды), которой в оригинале не было явно. Суть концепции теперь
   видна до погружения во внутренности.
2. **Убрал имена izi-ролей (Witt/Gilb/Wirth/Mills/…) из основного текста.** В оригинале была
   таблица на 15 строк с кодовыми именами и вкладами — для широкого читателя это шум. Свернул в
   один абзац «Роли-агенты (кратко)» со ссылкой на подробности.
3. **Свернул дословную цитату SemVer и алгоритм вопросов триажа (0–4)** в два простых абзаца:
   «вес решает один вопрос — совместимость» + «ловушка причина ≠ вес». Технический порядок
   вопросов оставил во flow-доках, куда дал ссылку.
4. **Объединил классификатор веса и таблицу вертикалей в одну таблицу «Пять вертикалей».**
   В оригинале это были две пересекающиеся таблицы (patch/minor/major «Причина/Следствие» +
   greenfield…chore «Дизайн/Бамп/Тоггл/Тесты»). Одна таблица + короткие пояснения к колонкам.
5. **Объяснил жаргон одной фразой при первом употреблении:** тоггл = фиче-флаг, пруф мерджа =
   «влит, не просто зелёный CI», скрытая деталь за интерфейсом = принцип Парнаса, 4 золотых сигнала = задержка/
   трафик/ошибки/насыщение, `.agent/` = служебная папка состояния.
6. **Стандарт разработки подал таблицей «Принцип · Суть · Следствие»** вместо нумерованного
   списка из 6 плотных пунктов — каждое утверждение сразу с следствием, как просил стиль.
7. **Убрал внутренние отсылки к скриптам** (`validate-contract-diff.mjs`, `close-run.mjs`,
   `semver-bump.mjs`, `ci/recipes/*`) из основного текста — они ничего не говорят внешнему
   читателю. Механику «закрытия прогона» описал по шагам словами.
8. **Выкинул мелкие внутренние оговорки:** pre-release/build-метадата, `DEFAULT_PREFIX`,
   VERSION-файла нет, K=2-предохранитель, `wip`-маркеры, режим `--hard`, лимит «≤300 строк».
   Это правила реализации, не суть концепции.
9. **Удалил Mermaid-диаграмму потока.** Для широкого читателя длинный граф с @-ролями сложнее
   текста; поток теперь описан прозой (гейты + канарейка + закрытие) со ссылкой на
   `docs/01_DIAGRAM.md`, где диаграмма — источник правды.
10. **Объём сократил примерно вдвое** (192 → ~135 строк). Все факты сверены с README,
    `docs/01_DIAGRAM.md` и `requirements/semver-verticals.md`.

### Места, где я сомневался — на ваше решение

- **Полный ростер ролей.** Я свёл 15 именованных ролей в один абзац. Если концепт должен
  оставаться и справочником по ролям — верните таблицу (можно в конец, под спойлер).
- **Научный фундамент и статьи автора** ужал: убрал список из 5 статей, оставил одну отправную
  точку. Если ссылки на все статьи важны для позиционирования — верну списком.
- **«4 золотых сигнала»** я расшифровал как задержка/трафик/ошибки/насыщение (стандарт Google SRE).
  В оригинале расшифровки не было — проверьте, что формулировка совпадает с вашим пониманием.
- **Форма проекта (service/cli)** из README я в концепт не вынес отдельной осью — упомянул только
  как «шаблон» в greenfield. Если вторая ось важна на уровне концепции — добавлю мини-секцию.
