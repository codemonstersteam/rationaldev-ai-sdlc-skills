# DEBT task-001: харнес не генерит async-`consumed-contract`

> **Тип:** технический долг харнеса · **Приоритет:** 🔴 P0 для эпика E0 экосистемы pinout
> **Скиллы-цели:** `skills/lib/component-tests` (генерация), `skills/lib/contract-tests` (маршрутизация)
> **Заказчик:** валидатор `pinout-asyncapi`
> **Вход заморожен** и является ТЗ: `debt/assets/task-001/` — менять эти файлы в рамках тикета нельзя.

## Суть

Валидатор совместимости принимает со стороны потребителя **не его AsyncAPI-спеку**, а артефакт
**`consumed-contract`** — узкую проекцию «какие каналы зову × какие поля шлю и читаю», захваченную из
компонентных заглушек и тестов потребителя, типизированную **из спеки поставщика** и снабжённую
штампом `provenance`. Спека AsyncAPI 3.0 остаётся контрактом **поставщика**; у потребителя её может не
быть вовсе — он не публикует API, он его потребляет.

Артефакт обязан рождаться механически, на той же фазе, где поднимаются стабы внешних зависимостей:
только там известно, какие поля реально используются. Написанный руками, он лжёт в обе стороны —
завышает охват (скопировали схему поставщика целиком) и протухает молча (штамп не пересчитан).

**Сегодня харнес этого не делает.** Слов `consumed-contract` / `provenance` в `skills/lib/` нет
(единственное вхождение — случайный пример в `documentation/SKILL.md:118`). Скилл `component-tests`
поднимает стабы, но контракт потребителя из них не извлекает и provenance не штампует. Следствие:
валидатор готов, а кормить его нечем.

## Заморожённый вход (вендорен, приёмка идёт против копий)

| файл в `debt/assets/task-001/` | что это |
|---|---|
| `consumed-contract.schema.json` | JSON Schema 2020-12, `x-frozen: 2026-07-25` — форма выхода генератора |
| `consumed-contract.golden.yaml` | эталонный артефакт на паре потребитель↔поставщик |
| `provider.asyncapi.v1.yaml` | спека поставщика той же пары — вход генератора |
| `PROVENANCE.md` | источник (репозиторий@коммит) + sha256 каждой копии |

Копии заморожены намеренно: приёмка не должна ходить в чужой репозиторий и в сеть. Разошлось с
источником — это факт для пере-вендоринга, видимый по хешам, а не тихий дрейф.

Форма — **канал × направление**:

```yaml
schema_version: "1.0"
consumer: mq-rest-sync-adapter
provenance:
  provider: wallet-balance
  provider_version: 1.4.0
  captured_hash: "sha256:<64 hex>"     # хеш байтов спеки поставщика на момент захвата
channels:
  - address: WALLET.BALANCE.REQUEST     # channel.address поставщика (fallback — ключ канала)
    protocol: kafka                     # из channel.servers -> server.protocol
    sends:                              # что потребитель ПУБЛИКУЕТ сюда
      - name: getBalanceRequest         # ключ map channel.messages (НЕ поле Message.Name!)
        content_type: application/json
        correlation_id_location: $message.header#/correlationId
        payload:  { type: object, properties: { clientId: {type: string}, … } }
        headers:  { type: object, properties: { correlationId: {type: string} } }
  - address: WALLET.BALANCE.RESPONSE
    protocol: kafka
    receives: [ … ]                     # что потребитель ЧИТАЕТ отсюда
```

Четыре нюанса формата, каждый — источник тихого бага при генерации:

| Нюанс | Правило | Почему |
|---|---|---|
| Ключ сообщения | ключ map `channel.messages`, **не** `Message.Name` и **не** ключ `components.messages` | парсер `lerenn/asyncapi-codegen` в `Specification.Process()` перезаписывает `Message.Name` Go-идентификатором (`GetBalanceResponse` → `GetBalanceResponseMessage`); ключи map при этом сохраняются. Опора на `Message.Name` = несовпадение пар на **каждом** сообщении |
| Нет поля `required` | в `schema` его **нет** намеренно; `properties` и есть множество используемых полей | контракт говорит, что потребитель ШЛЁТ и ЧИТАЕТ, а не чего требует. Лишнее поле никто бы не читал |
| Направления инвертированы | `sends` потребителя ↔ `action: receive` поставщика, и наоборот | ось всей модели; перепутать = зеркальный ложный вердикт |
| Только фактически используемые поля | не копировать схему поставщика целиком | смысл артефакта — узкая проекция. Копия схемы обнуляет ковариантную проверку: удаление поля поставщиком перестанет ловиться |

## Задача 1 — `skills/lib/component-tests`: генерировать артефакт

Добавить в **REALIZE**-половину шаг «захват `consumed-contract`», выполняемый там же, где поднимаются
стабы внешних зависимостей.

- [ ] Вход шага: спека поставщика (AsyncAPI 3.0) + компонентные заглушки и тесты потребителя.
- [ ] Выход: `component-tests/consumed-contract.yaml`, валидный против замороженной схемы.
- [ ] `payload`/`headers` — из **фактически используемых** полей заглушек и ассертов; `type`/`format`
      берутся **из спеки поставщика**, а не угадываются по значению из фикстуры.
- [ ] `protocol` — из `channel.servers → server.protocol` поставщика.
- [ ] `provenance` штампуется автоматически: `provider`, `provider_version` (`info.version` или коммит),
      `captured_hash` = sha256 байтов спеки. **Руками не пишется** — иначе штамп врёт.
- [ ] Детерминированность: те же заглушки ⇒ те же байты (сортировка ключей).
- [ ] Роутер-таблица «async-зависимость → шаг захвата» в стиле остальных скиллов, без суждений.
- [ ] STOP: спека поставщика недоступна · версия не 3.0.0 · канал без `address` и без ключа —
      остановиться и вернуть вопрос оператору, а не сгенерировать полуфабрикат.
- [ ] Anti-gaming: запрет копировать схему поставщика целиком в `payload` ради «зелёного».

- [ ] Контракт потребителя = `consumed-contract` (ссылка на замороженную схему в `debt/assets/task-001/`);
      AsyncAPI 3.0 остаётся контрактом **поставщика**.
- [ ] Отразить в Pass C1/C4: что генерится, куда кладётся, что именно сверяет валидатор.
- [ ] Добавить шаг конвейера потребителя: изменилась спека поставщика ⇒ **перегенерировать** стаб и
      `consumed-contract`. Не рекомендация, а гейт: устаревший `provenance` делает связь несвежей.

## Обоснование (почему обязанность лежит на харнесе)

Парадигма экосистемы: контракт потребителя **захватывается** инструментом, а не пишется человеком —
только захват гарантирует, что артефакт contract-true (описывает реально используемое) и свежий (штамп
привязан к байтам спеки поставщика). Валидатор при этом обязан быть самодостаточным: заказчик
заморозил формат у себя (решение D6) именно для того, чтобы не ждать харнес, и объявил доработку
`component-tests` внешней зависимостью экосистемы, а не своим блокером. Решение D8 (ключ пары —
ключ map `channel.messages`) — прямое следствие поведения парсера, проверенное на sandbox-спеке;
генератор обязан ему следовать, иначе валидатор захлебнётся ложными несовпадениями.
